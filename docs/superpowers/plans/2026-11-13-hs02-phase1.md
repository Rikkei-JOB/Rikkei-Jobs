## Contracts

- Internal identity: `GET /internal/users/{id}/lms-identity`, protected by the
  existing `X-Internal-Key`; returns `{userId,lmsUserId}` for an active candidate.
- Profile: candidate-only `GET /profiles/me` creates a PRIVATE profile on first
  access, calling identity then `/lms/students/{lmsUserId}` using server-side keys.
  Existing profiles remain readable if dependencies are offline.
- `PUT /profiles/me` accepts fullName, email, dob, gender, phone, address,
  headline and summary. Unknown/protected fields are ignored. LMS fields,
  owner, avatar and visibility cannot be changed through this request.
- Response includes userId, the editable fields, avatarUrl, program, classCode,
  courseName, visibility and updatedAt. Gender: MALE/FEMALE/OTHER or null.
- Name/email required, max 255; phone optional `0` plus nine digits; date of
  birth cannot be future; address max 500, headline 255, summary 5000.
- Migration V5 adds candidate_profiles without modifying V1-V4. Concurrent first
  access uses the existing per-user profile state lock to prevent duplicate rows.
- Failures upstream return structured 502/503, missing LMS link/student 404;
  incomplete or mismatched upstream records must never create partial profiles.
