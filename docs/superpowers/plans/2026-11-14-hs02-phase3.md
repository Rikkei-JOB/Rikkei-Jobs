# HS-02 phase 3 implementation plan

Approved scope: self-declared skills, HS-01 integration, complete HS-02 automated
regression and handoff docs. Work in existing clean feature/HS-02, baseline b5e576c.
No commit/push/PR or live candidate profile edits. Keep phase 1–2 and HS-01 intact.

## Contracts

- GET `/api/v1/skills` returns all catalogue skills, sorted group/code, as
  `[{id,code,name,group}]`, requiring a valid authenticated user. Add gateway route
  to profile-service; no hardcoded frontend catalogue.
- PUT `/api/v1/profiles/me/self-skills` (CANDIDATE only) consumes the exact JSON
  array `[{skillId:UUID,selfScore:number}]`, returns complete updated SkillProfileView[]
  (same shape as GET /profiles/me/skills). Full replacement of current user's SELF
  collection; [] clears only SELF. Unknown/duplicate/null skill, missing/null score,
  score outside 0–100 or >6 decimal places returns 400, leaving all old data intact.
- Save under existing per-user profile lock, shared with import/recompute; remove
  only this owner's SELF evidence, then create one canonical SELF evidence per skill
  (sourceRef self, title Tự khai, weight 1, verified false, externalRecordId null).
  Update skill_scores.self_score atomically; clear omitted self scores and delete
  an empty self-only score row. Preserve all non-SELF evidence, verifiedScore,
  level and other users' data. Recompute must retain self scores afterwards.
- No new schema is required: existing skill_evidences/skill_scores support SELF.
  Ensure dev demo seeding does not restore removed SELF skills on restart; demo
  SELF is only seeded when a profile state has never existed.
- Frontend at /candidate/profile: add a self-assessment form using catalogue and
  current selfScore, add/edit/remove rows, validate duplicates/range, show errors
  and preserve input on save failure. Explain scores are self-declared and don't
  affect verified score. Refresh existing HS-01 immediately after successful save;
  preserve viewing-only public skill profile behavior and phase 1–2 cards.

## Work and checks

1. Backend (root): API tests RED, then catalogue controller, DTO, self replacement
   service/controller integration and seeder adjustment. Test full round trip,
   atomic validation, auth/roles/ownership, stale self-only score cleanup, preserved
   verified scores/evidence, recompute and repeated/concurrent saves. Gateway RED
   then add catalogue route. Document API and complete HS-02 acceptance checklist.
2. Frontend (web only): Playwright RED then implementation/GREEN. Cover add/edit/
   remove/clear, badge and score refresh, validation, error retry preserving input,
   authenticated calls. Type-check/lint/build, whole existing e2e suite and visual
   desktop/mobile QA with API doubles (no live data edits).
3. Regression: full backend suite where dependencies permit; relevant PostgreSQL
   tests on isolated test DB including phase 1–2 and self-skills; fresh independent
   review, fix proven issues, update running profile/gateway+frontend for user to test.

Review focus: null/duplicate/unknown skills roll back entire replacement; deletion
never touches non-SELF or another owner; concurrent save/recompute produces consistent
evidence/selfScore; demo startup doesn't resurrect removed skills; public skill page
never shows editable controls; empty arrays remain empty after refresh/restart.
